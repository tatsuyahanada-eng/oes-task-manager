# 複数人で使う — 置き場所の選び方

「サーバに置いて、社内の複数人で管理・運用したい」への回答です。

---

## 0. 結論から

| | 置き場所 | 費用の目安 | 向き不向き |
|---|---|---|---|
| **推奨** | **VPS 1 台**（さくら / ConoHa / Xserver VPS など） | 月 600〜1,000 円 | 社内の複数人で使う本命 |
| 次点 | 社内サーバ / NAS（Docker 可のもの） | 0 円（既にあれば） | 社外から使わないなら最も安全 |
| 検証用 | 手元の PC | 0 円 | 1 人での動作確認用 |
| **不可** | ロリポップなどの共用レンタルサーバ | — | Node.js の常駐プロセスが動かせない |

**ロリポップに置く案は、残念ながら成立しません。** 理由は次章のとおりです。

---

## 1. なぜロリポップではダメなのか

理由は 2 つあり、**どちらも設定では回避できません。**

### 理由 1 — Node.js の常駐プロセスが動かせない

DB Controller は `server.js` が起動しっぱなしになっている必要があります。
PHP のように「アクセスが来たら実行して終わる」形ではありません。

共用レンタルサーバは PHP 向けで、常駐プロセス（デーモン）の実行を認めていないのが一般的です。
FTP でファイルを置いても、それを動かす人がいない、という状態になります。

### 理由 2 — MySQL のホスト名が `.lan` で終わっている

```
mysql151.phy.lolipop.lan
```

`.lan` はインターネット上に存在しない、**ロリポップの内部だけで通じる名前**です。
外部の PC やサーバからは、名前を引くことすらできません。

```
$ getent hosts mysql151.phy.lolipop.lan   →  （応答なし）
$ getent hosts lolipop.jp                 →  133.130.34.142
```

つまり **「ロリポップ上でツールが動かせない」かつ「外からロリポップの DB へ届かない」** という、
両側が塞がった状態です。

> ロリポップの管理画面に外部接続用の別ホスト名（`.jp` などで終わるもの）が
> 案内されている場合は、そちらを使えば「外から届かない」側は解決します。
> それでも「ツールを置く場所」は別に用意が要ります。

---

## 2. 推奨する構成 — VPS 1 台

```
   社内の PC / スマホ
        │  HTTPS（社内 IP からのみ許可）
        ▼
   ┌─────────────────────────┐
   │  VPS                    │
   │   nginx  … HTTPS を受ける   │
   │     ↓ 127.0.0.1:3000       │
   │   DB Controller (Node.js)   │
   └──────────┬──────────────┘
              │
     ┌────────┼────────────────┐
     ▼        ▼                ▼
  Oracle   SQL Server      PostgreSQL / MySQL
```

**この構成の良いところ:**

- 全員が同じ URL を開くだけ。各自の PC に何も入れなくてよい
- 接続先の登録が 1 か所で済む。担当者ごとに設定がばらけない
- 誰が何をしたかが `data/audit.log` に一本化される
- スマホからも使える（PWA なのでホーム画面に追加できる）

**必要な作業:**

1. VPS を契約し、Node.js 22 を入れる（`DEPLOY.md` §2）
2. DB Controller を `~/apps/db-controller/` に置く（**公開ディレクトリには置かない**）
3. `systemd` で常駐させる（`DEPLOY.md` §9）
4. nginx で HTTPS を張り、`127.0.0.1:3000` へ中継する（`DEPLOY.md` §8-3）
5. **社内の固定 IP からのみ許可する**（`DEPLOY.md` §8-4）
6. 管理者でログインし、利用者を登録する（次章）

## 3. 利用者と権限

複数人で使うために、**利用者を何人でも登録できます。**
できることは 3 段階に分かれます。

| 役割 | 利用者の管理 | 接続先の登録・変更 | データの変更 | データの参照・CSV 出力 |
|---|:---:|:---:|:---:|:---:|
| **管理者** admin | ○ | ○ | ○ | ○ |
| **運用者** operator | × | × | ○ | ○ |
| **閲覧者** viewer | × | × | **×** | ○ |

### 誰にどれを割り当てるか

- **管理者** … DB の接続情報（ホスト・ユーザー・パスワード）を扱える人。少人数に絞ってください
- **運用者** … 日々のメンテナンス担当。データは直せるが、接続先の設定は触れない
- **閲覧者** … 状況を見たいだけの人。**間違って消す事故が起こりません**

### 使い方

1. 管理者でログイン →「設定」タブ
2. 「利用者」欄の **「+ 利用者を追加」**
3. ユーザー名 / 役割（`admin` `operator` `viewer`）/ 初期パスワードを入力
4. 本人に伝え、**初回ログイン後に本人がパスワードを変更**してもらう

役割の変更・利用停止・削除も同じ欄から行えます。

> **変更はその場で効きます。** 誰かを利用停止にすると、その人が画面を開いたままでも
> 次の操作から弾かれます。役割を下げた場合も同様です。

### 守りは画面だけではありません

画面上でボタンを隠すのは「押し間違いを防ぐため」で、守りの本体ではありません。
**サーバ側でも同じ制限をかけています。** 画面を細工したり、API を直接叩いたりしても、
権限のない操作は `403` で拒否されます。

## 4. 二重の安全装置

データを壊さないための仕組みが、**利用者の役割とは別に**もう一段あります。

| | しくみ |
|---|---|
| **接続ごと** | 「読み取り専用」を付けた接続からは、誰であっても変更できない |
| **利用者ごと** | 閲覧者は、書き込み可の接続に対しても変更できない |

**両方を満たさないと書き込めません。**
移行元の本番 DB は「読み取り専用」にしておけば、管理者が操作しても壊れません。

さらに、実際の更新には次の条件がかかります。

- 対象テーブルに主キーがあること（行を一意に特定できること）
- トランザクション内で実行し、**影響行数がちょうど 1 行**であること（違えばロールバック）
- `WHERE` の無い `UPDATE` / `DELETE` は、明示的に同意しない限り実行しない
- `DROP` などの DDL は受け付けない

## 5. 共有環境に置く前の必須チェック

`DEPLOY.md` §11 のチェックリストに加えて、複数人で使う場合は次を必ず確認してください。

```bash
# 1. 初期パスワードの利用者が残っていないか
#    残っていると、localhost 以外での起動を拒否します
node server.js
#   → 「※ パスワードが初期値のままの利用者がいます: ...」が出ないこと

# 2. 認証なしでアクセスできないか（401 が返れば正しい）
curl -s -o /dev/null -w '%{http_code}\n' https://社内URL/api/connections

# 3. data/ が Web から見えていないか（404 か 403 が返れば正しい）
curl -s -o /dev/null -w '%{http_code}\n' https://社内URL/data/auth.json
curl -s -o /dev/null -w '%{http_code}\n' https://社内URL/data/.masterkey

# 4. HTTP が HTTPS に飛ぶか（301 が返れば正しい）
curl -s -o /dev/null -w '%{http_code}\n' http://社内URL/
```

**2 と 3 は、1 つでも通ってしまったら公開を中止してください。**
`data/.masterkey` は、保存された DB パスワードを復号する鍵そのものです。

## 6. 手元の PC でやる場合との違い

「まず動かしてみる」段階では手元の PC で十分ですが、共有には向きません。

| | 手元の PC | 共有サーバ |
|---|---|---|
| 他の人が使える | × | ○ |
| その PC の電源を切ると | 止まる | 関係ない |
| 接続先の登録 | 各自がそれぞれ行う | 1 か所にまとまる |
| 操作履歴 | 各自の PC にばらける | 1 か所にまとまる |
| 準備の手間 | 少ない | HTTPS・常駐・IP 制限が要る |

**移行作業そのものは手元の PC でも進められます。**
共有環境の準備と並行して、手元で検証を進めるのが現実的です。

## 7. ロリポップの DB を使い続ける場合

DB がロリポップにあり、動かす場所が VPS や社内サーバになる場合、
`.lan` の壁は残ります。次のいずれかになります。

**A. 管理画面で外部接続用のホスト名を確認する**

`.jp` などで終わる名前が案内されていれば、それを使ってそのまま接続できます。

**B. SSH ポートフォワードを常時張る**

```bash
# 動かす側のサーバで、autossh などを使って張りっぱなしにする
ssh -N -L 13306:mysql151.phy.lolipop.lan:3306 アカウント名@ssh.lolipop.jp
```

DB Controller には `127.0.0.1:13306` として登録します。

**C. DB ごと移す**

そもそもの目的が移行なら、**移行先を VPS 上の PostgreSQL / MySQL にしてしまう**のが
いちばん素直です。`.lan` の制約からも、共用サーバの性能上限からも解放されます。

## 8. どこまで確認済みか

| | 状況 |
|---|---|
| 利用者の追加・役割変更・停止・削除 | ○ 確認済み |
| 権限による API の拒否（サーバ側） | ○ 確認済み（32 項目） |
| 権限による画面の出し分け | ○ 実ブラウザで確認済み（20 項目） |
| 旧形式 `auth.json` からの自動移行 | ○ 確認済み（既存のパスワードのまま） |
| MySQL / MariaDB での参照・追加・修正・CSV | ○ 確認済み |
| PostgreSQL での参照・更新 | ○ 確認済み |
| **Oracle / SQL Server** | **× 実サーバで未確認**（手元に検証環境がないため） |
| **VPS への設置そのもの** | **× 未実施**（手順は `DEPLOY.md` に記載） |
